## TD-20261101-09：候选高频保护将嵌套显式项目错误计入热点祖先

- 日期：2026-11-01（Asia/Shanghai）
- 状态：已修复，旧候选失败、修复后通过；未进入已发布版本。
- 影响版本与环境：PR #56 的 f09ff77 / f210e59 候选，仅 upload_rate_roots 存在重叠的显式根时。
- 关联历史故障：TD-20261101-07 的候选修复遗漏，由 Dot 静态审查发现；不是本机既有 0.2.21 的回归。

### 症状与影响

外层项目预算已耗尽后，一个单独指定的嵌套项目也被错误延期，会影响正常上传隔离。没有生产数据变更或发布影响。

### 触发条件与复现

配置 /source/project 和 /source/project/nested 两个根，关闭单文件预算、项目预算设为 1。先使外层项目热点并耗尽，再对内层文件连续上传不同修改代次；第二次修改不应消耗外层预算。虚拟时间回归在 f210e59 上实际失败：another configured root must not consume nested/inner's budget。

### 根因与证据

acquire 在 hot_projects 中找到祖先后就跳过 project_root，因此没有执行最具体的显式根选择；补算项目历史时也会把显式嵌套根的记录计入外层。Dot 的源级示例只是静态推断；新增测试才是本次实际复现证据。

### 解决办法与恢复操作

先做纯内存的最具体显式根匹配，再复用该根的热点预算；冷的显式子项目不会继承热点祖先。补算历史时使用相同归属规则，排除其他显式根。不新增正常路径文件系统探测；没有本机恢复操作。

### 验证结果与边界

explicit_nested_projects_keep_separate_budgets_in_either_discovery_order 分别验证先外后内、先内后外，两项目各自可用一份预算并独立达到限额；项目标志元数据探测仍为 0。daemon 21 项测试与严格 Clippy 通过；全量最终检查和 PR 当前提交复审待补充。没有真实云端测试。

### 防复发措施与后续

保留双顺序、虚拟时间、额度隔离与零项目探测断言。合并前重新检查最终提交的 Dot 回复及 CI，不把旧提交的审查结论转移到新提交。

## TD-20261101-08：特殊目录快照无法区分同秒等长的连续保存

- 日期：2026-11-01（Asia/Shanghai）
- 状态：已修复，隔离回归通过；待 PR/CI 与发布交付。
- 影响版本与环境：0.2.21 及此前使用 size + 秒级 mtime 的特殊目录快照。
- 关联历史故障：TD-20261101-07 排查编辑器自动保存时发现的相邻机制；不据此宣称现场发生过内容丢失。

### 症状与影响

同一秒内、长度不变的内容改写可能被当成已上传，或在上传前后发生变化却未被识别。原现场没有逐代内容证据，实际影响范围未确认。

### 触发条件与复现

隔离文件设置为相同整秒、分别 100ms 和 200ms 的 mtime，长度相同。旧 size/modified_unix 签名完全相等，新快照必须不同。

### 根因与证据

FileSnapshot::from_metadata 将 mtime 截断为秒，扫描跳过判断和上传前后验证复用了同一签名。高频保护也需要可区分保存代次，不能继续沿用这个精度。

### 解决办法与恢复操作

快照和增量状态保存纳秒部分；旧 JSON 导入时，若文件的旧大小/整秒仍匹配，则从只读本地元数据补齐纳秒，避免迁移后重传全部未变化历史。旧实现已遗漏的同秒改写不能凭迁移反推，未执行历史内容恢复。

### 验证结果与边界

same_second_same_size_changes_have_distinct_snapshots 证明旧签名相同、新签名不同；旧状态导入和上传前后保护测试通过。未比较真实云端历史内容；文件系统若自身不提供足够时间精度，仍有边界，未增加全文件内容哈希或额外轮询。

### 防复发措施与后续

保留高精度代次与迁移回归。不能将一次长度/时间元数据检查描述为完整内容哈希验证。

### 交付记录

随 0.2.22 修复；提交、PR、Release 待补充。

## TD-20261101-07：开发目录触发特殊目录上传高负载及重复目录冲突

- 日期：2026-11-01（Asia/Shanghai）
- 状态：负载放大机制已修复，隔离测试通过；待 PR/CI、正式制品及本机更新。
- 影响版本与环境：本机 0.2.21，Linux 特殊目录 upload_only 后台；用户在上传来源目录内进行开发。
- 关联历史故障：[2026-09-11 目录移动竞争](folder-move-sync-2026-09-11.md) 同样出现 409，但本次为特殊目录上传路径，没有证据表明是同一根因。相邻快照精度问题见 TD-20261101-08。

### 症状与影响

用户报告后台线程间歇占满单核；随后占用下降。只读日志统计近两小时有 111 条 409；采样同一线程四秒内消耗约 1.04 秒 CPU。状态约 20,471,497 字节，含 12,802 个已传快照和 52,783 个待传项，其中 52,772 个待传项位于 node_modules，三秒内状态文件发生重写。没有确认系统崩溃或内容丢失。

### 触发条件与复现

Pictures/Downloads 特殊目录上传开启，startup_scan=true、rescan_interval=15m，开发工具在来源下创建大量依赖文件。四项新增测试在旧代码上失败：依赖目录未排除、隐藏祖先的事件绕过过滤、待处理事件无容量约束、已有远端目录持续重建且不检查同名文件。

### 根因与证据

1. 排除只检查最后一级，默认不排除 node_modules，已持久队列重试不应用当前规则。只给开发目录添加扫描后缀排除仍无法阻止其子文件事件重新建队列；实际只读复查确认再次出现该项目任务。
2. 每个文件结果都会序列化并 fsync 整份 JSON。队列含数万项时，总工作量随结果数乘以全表规模增长；这解释了可复现的放大机制，但未取得现场 CPU 调用栈，不能宣称已量化所有 CPU 来源。
3. notify 入口和去抖集合无上限，父子路径可能重复扫描；持续活动可无限延长原来的全局去抖。新增入口回归覆盖容量溢出与系统 Rescan 标记。
4. 目录创建错误只记日志并继续，没有查询已有目录的身份并写回数据库，也没有拒绝同名文件。

### 解决办法与恢复操作

扫描、事件入口及队列重试统一检查每一级路径；默认 exclude_names=["node_modules"]。已有开发目录的整树排除保存在本机配置，不随源码发布。事件入口最多保留 1024 个载荷，溢出通过过滤后的来源重扫恢复；父子事件合并。支持原地写入和原子保存，默认 5 秒去抖、连续活动最长等待 30 秒。

首次上传、不同文件的普通首次修改、同一已准入代次的网络重试不占项目高频预算。反复修改采用滑动时间窗口：单文件 20 秒 25 次，热点项目 20 秒 180 次；超过后持久延期并重试最新源，不限制每批数量、不更改配置并发。正常事件只做内存计数，单文件或累计反复修改达到高频阈值才识别项目根；最多向上八层、不越过来源，标志和未命中结果均缓存一个窗口，可用显式 upload_rate_roots 覆盖。无额外空闲目录搜索；仅有延期任务时才缩短重试唤醒。

状态迁移到独立 known-folders-state.sqlite3：旧 JSON 在一个事务中导入并保留作回退快照，成功结果只更新自己的快照与队列行；先持久排队再发云端操作，单项进度在慢任务完成前仍可读。创建远端目录前先读取已有对象，创建竞争失败后复查，拒绝同名文件并保留失败任务。

本机止血单独执行：两次均先检查挂载没有可写描述符及 writing/dirty/uploading/conflict 记录，私有备份配置和队列后停止后台以免竞写；第一次取消 51,280 个该项目的旧任务并加入扫描排除。复查确认旧版事件漏洞又建队列，第二次再取消当时剩余的 17 个任务并临时关闭特殊目录自动上传，保留正常挂载读写。之后四秒采样 CPU 为 0.0%、队列前后均为 0。没有删除任何源文件或云端副本；软件更新后需恢复其他来源上传。备份清单和完整路径仅在本机私有目录保留。

### 验证结果与边界

四个原缺陷回归已证明旧代码失败、修复后通过。当前 21 项 daemon 测试通过，包括实际队列持久化/重试最新内容、并发上传、先完成结果的耐久性、滑动窗口边界、首次大批任务不计预算、事件入口溢出、目录排除及项目探测开销。项目功耗回归确认前 25 次的项目元数据探测为 0，第 26 次才识别，之后缓存命中不新增探测；正/负缓存各用 1000 次查询验证，另用 1000 个不同未知父目录验证一个窗口最多八次冷搜索（最多 512 次标志元数据探测）。原全量 228 项 Rust 测试通过、11 项依赖环境而忽略，25 项 Nautilus、4 项 Settings、2 项锁文件及 6 项发布保护通过，格式和严格 Clippy 通过；新增搜索总预算回归通过。发布验证待补充。

增量存储回归在 1000 个无关快照旁完成一项任务，SQLite 实际仅改变 2 行，旧 JSON 字节保持不变，重开后队列与快照正确。未主动制造真实 OneDrive 测试写入；模拟 backend 不代表真实云端端到端。未通过断电试验证明全部存储栈耐久性，也未量化整机功耗。

## TD-20261101-05：恢复副本完成后原路径仍可见并显示同步失败

- 日期：2026-11-01（Asia/Shanghai）
- 状态：已验证修复（模拟云端的单元/实际 FUSE 回归、真实文件名恢复及本机 0.2.21 部署）；真实云端竞争未主动重放。
- 影响版本与环境：本机 0.2.20；后台完成缺失云端对象的冲突副本保全后。
- 关联历史故障：TD-20261101-01、TD-20261101-02；属于恢复完成后的 FUSE 命名空间遗漏，历史云端删除行为的执行者仍未确认。

### 症状与影响

用户报告原文件名仍显示同步失败。原路径的 status-path 为 unknown/error，数据库和真实云端只有已完成的恢复副本；原路径却仍能 stat/read。针对该文件读取的两份已缓存内容长度及 SHA-256 一致，未发现内容丢失。

### 触发条件与复现

后台完成 missing-target conflict recovery 并退休原数据库行后，不扫描目录，直接 stat/read 原文件名。新增隔离实际 FUSE 断言在 0.2.20 上稳定失败：`retired source remains visible after recovery`。另两个单元回归分别证明退休 inode 仍返回旧记录、不同身份复用相同路径时共享 inode。

### 根因与证据

lookup 优先使用内存路径；record_for_ino 只返回缓存记录，refresh_record 在数据库身份和路径均不存在时仍回退旧记录。后台事务已经移除原行，却不能同步更新挂载进程内的 InodeTable，getattr/lookup 因此持续成功，桌面查询数据库则得到 unknown/error。另 refresh_children/insert_or_update 仅凭路径复用 inode，可能把仍打开的旧身份与后来同名的新身份混在一起，旧 inode 更新/移除还会无条件删除新所有者的路径映射。

### 解决办法与恢复操作

按数据库身份解析现有 inode，不再以同名的另一个数据库身份刷新旧记录；lookup 优先选择现有路径所有者，拒绝已经退休的身份。保留仍在数据库中的、被 delta 移动的身份在目录刷新前支持幂等改名的兼容行为。开放描述符继续读取其原缓存，退休后 fstat 返回 nlink=0，并从已打开缓存取得当前大小。不同身份重用路径时分配不同 inode；移除旧路径映射必须仍拥有该映射，目录输出排除失去映射的旧项。

本机恢复单独执行：核对无该文件的开放句柄、数据库原路径为空、真实云端原文件名不存在，两份缓存字节一致后，将已保全副本通过正常挂载改回用户指定的原文件名。未直接编辑 SQLite、没有覆盖另一个云端文件。完成后真实云端同一 ID 返回原名称、63870 字节和相同服务器内容校验值；本地 cached/synced，metadata_operation_pending=false。路径、ID、内容摘要和恢复快照仅保存在本机私有维护目录。

### 验证结果与边界

### 触发条件与复现

用户随后补充：在上传完成前改过文件名，原名包含 Windows/OneDrive 不支持的 ASCII 冒号。进一步按完整文件名边界重新解析日志，确认同一文档 2026-10-31 22:03:14 的带冒号改名收到 HTTP 400 / invalidRequest；去除冒号后 22:03:28、22:03:55、22:04:02 的改名及 22:04:55—56 的上传收到 423 / resourceLocked，随后服务停止。初诊宽泛关键字还匹配了其他文档，不将其较早锁定记录算作本文件的精确时间线。

真实云端只读核对：原父目录可访问，其身份与本地绑定相同；旧文件 ID 的独立元数据 GET 也返回 404，父目录列举没有该文件，文件编号搜索无结果。该结果确认旧绑定当前不可用；不能仅凭搜索为空证明永久删除，也不能确定由用户、其他客户端还是 TwoDrive 的哪次操作移除。

受控复现之一：初次 PUT 已在模拟云端创建对象但确认被延迟 → 本地先改名（分别覆盖含冒号与合法中间名）→ 云端 delta 回显旧路径并建立别名 → 再将本地源替换到该别名 → 旧上传确认迟到。旧程序找不到原本地身份，把返回的云端 ID 当作孤立对象排入删除，而目标记录正在合法持有同一 ID；执行恢复删除后，模拟云端对象确实消失。此测试使用真实 Rust/SQLite 调用链和 MockBackend，不能冒称昨晚真实 OneDrive 时序已完整重放。

### 根因与证据

1. **迟到确认的清理没有检查当前所有权**：`recover_dirty_record` 提交失效本地身份失败后调用 `queue_remote_delete`；旧 SQL 无条件入队，删除执行也不复验该云端 ID 是否已被另一活动记录接管。上述受控竞争能真正删除仍有活动本地所有者的模拟云端对象。原现场没有逐项上传/删除关联日志，故这属于已证实的相关缺陷，尚不是排除了所有其他解释的历史唯一根因。
2. **原子保存取消了目标的待改名操作**：`replace_file_locally` 清除源、目标双方元数据待办，但替换保留的是目标的云端身份；如果目标刚被本地改名，其云端 move 仍必须执行。旧代码会保留本地新名和内容，却丢失改名待办。独立 SQLite 回归证明旧行为失败。
3. **文件名验证路径不一致**：上传预先拒绝 `:` 等字符；Graph rename/create_folder 没有同样检查，会先取令牌并向云端发送无效名称。真实 400 与这条路径吻合，ASCII 冒号会阻塞改名；这本身不能证明会删除文件。新增回归以过期合成令牌验证无效名称必须先被本地拒绝，旧实现失败。
4. **缺失上传目标没有恢复出口**：Dirty 代次每次仍向旧 ID PUT，404 后又回到 Dirty；既有冲突保存也要求原对象继续存在，原对象已缺失时会在上传副本后失败并重复重试。这解释持续 404 与活动显示，即使当日没有用户写入也会发生。

微软 [delta 文档](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0)以 deleted 标记表示删除；[内容上传文档](https://learn.microsoft.com/en-us/graph/api/driveitem-put-content?view=graph-rest-1.0)区分按既有 ID 更新与按父项/名称新建。本地保护未上传字节是必要的，但不能据此永久重用已失效的云端身份。

### 解决办法与恢复操作

- 孤立上传清理入队时原子检查 ID 没有活动所有者；执行旧清理任务时再次检查。已被活动记录接管的孤立清理取消，真正本地删除待办遇到冲突所有权时保留，不能删除活动对象。
- 原子替换只取消源记录的过时元数据任务，保留目标的云端改名任务及身份。初传确认前的 delta 回显只在路径、云端版本、大小全部匹配，且别名没有本地修改、显式固定或待处理移动时与原本地身份合并，避免云端 ID 唯一约束错误和旧名重复项；别名旧缓存进入受引用/文件锁保护的退休队列。
- rename/create_folder 与上传共享名称预检，先于鉴权或网络；本地未上传的非法名称仍可修正为合法名称后正常恢复。
- 仅对数据接口的类型化 404 做旧 ID 元数据复核，确认缺失后保存独立 `TwoDrive conflict` 副本，不按原名复活删除对象或覆盖同名新对象。副本登记、旧代次有条件移除及上传声明清理在同一 SQLite 事务中完成；新保存/打开写入的代次不得被旧失败转成冲突或删除。

调查与开发均使用隔离 worktree、低优先级和两路编译；未为调查主动读现用挂载内容、手动 sync、改生产数据库或制造真实云端写入。独立本地恢复/安装结果见交付补记；不能把受控竞争测试当作历史现场已完整重放。用户指定的完整修复/发布/清理流程已持久写入 AGENTS.md。

### 触发条件与复现

原操作时序未确认。隔离 SQLite/MockBackend 的稳定复现：缓存版本 A 后，按同一云端身份导入 ETag 或 size 改变的版本 B；旧实现仍返回 cached/pinned 和 A 的缓存路径。缩小导致读取被 B 的 size 截断，增大则可能提前到达旧缓存 EOF，同长度编辑也会继续读取旧内容。另一个复现是在 A 的下载开始后导入 B，再尝试发布 A 的迟到结果。没有对真实用户文件制造写入、截断或云端更新。

### 根因与证据

`database/metadata.rs` 的单项和批量 upsert 原来只替换 size/ETag/mtime，未同时解除旧 cache_path、撤销 cached/pinned 状态或递增 download_generation。hydration/open 只判断缓存是否存在，故继续信任另一版本的字节。`attr_for_record` 使用元数据 size；read_slice 没有主动按元数据裁剪，但内核使用 FUSE 返回的 i_size 判断 EOF。由此可把旧文件前缀呈现为一个较短文件，而非完整的新云端文件。

另有两项放大因素：inode 表只在目录刷新等路径更新，getattr 可一直返回旧快照；文件属性 TTL 为 30 秒。旧读取句柄还会按缓存路径重新 open，缓存被替换后可能跳到另一份文件，而非继续读其持有的描述符。原现场只读结果确认“当前云端元数据 + 不同内容缓存”的组合，尚未保存最初写入、上传确认、delta 的逐操作轨迹，不能宣称已还原具体哪个 Office/设备操作造成这一组合。

### 解决办法与恢复操作

- 将单项/批量导入统一到 Immediate 事务，事务内核验本地内容状态与待办；远端 ETag 或 size 改变时原子解除缓存引用、增加下载代次，保留磁盘旧字节。Writing/Dirty/Uploading/Conflict 不被远端导入覆盖；冲突副本已经保全后，显式解除原对象保护再导入云端获胜版本。
- 同版本回声和纯路径移动保留缓存及本地 mtime；保留单项/批量新条目的既有 pin 继承差异。
- 干净缓存长度不符时，按快照条件解除引用并重新下载，不把较长缓存当成待上传内容。新下载采用包含代次的缓存路径，旧缓存留作打开句柄或恢复材料。
- 下载前后核对远端 ETag/size，拒绝下载期间的版本变化、错误长度和已取消代次；发布事务再次核验实际临时文件长度。并发云端变化可能使本次读取取消，待元数据更新后重新打开；不把一次取消伪装成成功。

- 状态：已修复并验证受控竞争机制，修复构建已部署本机；后续发布验证和交付状态见下方 PR/Release 记录。原现场完整刷新时序未确认。

### 症状与影响

用户报告将已有 PDF 移入同一挂载内的子目录时，文件管理器提示 Input/output error。17:58:22.175958（Asia/Shanghai）daemon 记录 `twodrive rename error: local replacement disappeared`。随后只读查询显示源路径、目标路径及同名文件均不在本地索引中。错误提示本身不能证明 PDF 内容损坏。

真实 Graph 只读核对曾得到源路径 404、目标路径 200，目标文件为 244,856 字节；随后原目标也返回 404，同名搜索为空。用户确认排查期间仍在整理、移动文件，之后告知已完成。不能把后续路径变化当成软件再次删除云端文件的证据，最终云端位置尚未确认。

### 触发条件与复现

未主动移动用户文件。隔离 MockBackend 与临时 SQLite 的最小复现：

1. 缓存一份已绑定云端身份的文件，FUSE inode 仍指向旧目录条目。
2. 模拟云端已移动该文件，导入更新后的元数据，但不刷新旧目录。
3. 刷新目标目录；同一身份可同时由旧路径 inode 与新路径 inode 表示。
4. 从旧目录视图再次执行相同目标的 rename。

新增 `stale_source_inode_rename_preserves_file_already_at_destination` 显式运行后稳定失败，报告 `rename deleted the existing local identity: Err(local replacement disappeared)`，与实际日志的内部错误一致。

### 根因与证据

`filesystem/mutations.rs::rename_record` 先通过旧路径取得 inode，再按身份读取数据库中的最新源记录。若后台元数据已将该身份移动到目标，源与目标可成为同一条记录，但代码仍调用 `Database::replace_file_locally`。

`database/mutations.rs::replace_file_locally` 未拒绝或短路相同 source/target 身份：事务先 DELETE 源，再 UPDATE 已被删除的同一目标；UPDATE 行数未校验，事务仍提交。事务后查询目标为空，返回 `local replacement disappeared`，FUSE 再将其映射为 EIO。隔离测试确认本地记录被删除；该复现中云端对象与原缓存字节未由这一事务删除。

实际错误前约 2.5 秒有一次 delta 导入完成；当时日志没有保留该 PDF 的源/目标身份及逐操作轨迹。因此已确认可导致完全相同错误的缺陷及其触发条件，但不能把模拟时序冒称原现场完整重放，也未排除原现场的其他并发删除窗口。

## TD-20261015-16：同实例元数据写者竞争耗尽 SQLite 锁等待

- 日期：2026-10-15（Asia/Shanghai）
- 状态：已验证受控旧失败/新通过与错误后放行；最终 Linux/Windows 候选检查见 PR #30。原历史 Windows 宿主的逐操作时序仍不可追溯。

### 症状与影响

八 writer 各写二十条时可返回 SQLite Busy，导致部分调用报错而非完成全部 160 条。没有已确认的用户数据损坏。原 native Windows 日志只有 join 处的 error code 5，不能从它推断具体语句。

### 触发条件与复现

诊断候选 a9c28c7 增加静态阶段、合成 worker/序号、耗时及扩展码。Linux 十轮单项、独立 20/40ms sync 延迟均通过；Windows 原 core 套件加八轮默认并发、随后八轮 32 测试线程的 core 复验也全部通过，证明原故障并非每次出现。

保留 scripts/test-database-contention.sh：仅在 disposable core 测试进程中预加载 fixture，将 fsync/fdatasync 放到共享队列并各延迟 40ms，32 个测试线程并行。旧代码实测 39 passed、1 failed，100.54 秒；同一并发写入测试报告 writer=0 item=0 elapsed=10.0536s sqlite_code=5，阶段为 metadata upsert: beginning write transaction。这是可控共享存储竞争，不是原 Windows 宿主的精确重放。

### 根因与证据

Database clones 共享路径但没有共享元数据写入准入；每次 upsert 先提交元数据事务，再开启单独的全表 pin 重算事务。竞争者可在多个事务之间反复取得唯一写锁，使等待中的调用在事务开始处耗尽十秒 busy_timeout。受控日志定位到 BEGIN，排除了该复现中的快照升级或 WAL 读恢复错误。SQLite 只允许一个 writer，busy handler 不是应用级完整操作的排队协议；见 [SQLite isolation](https://www.sqlite.org/isolation.html) 与 [busy handler](https://www.sqlite.org/c3ref/busy_handler.html)。历史 Windows 原始日志缺少阶段，仍不能证明当时每一步与本次完全一致。

### 解决办法与恢复操作

Database clones 共享一个元数据写入 Mutex；单条和批量导入均在准入后完成整次元数据更新、后代移动和 pin 重算，返回或出错时释放。读取不取该锁，其他 Database 实例和进程继续由 SQLite 仲裁。十秒 SQLite 超时、Immediate 事务、持久化、八 writer/160 条断言均保留，不吞掉 Busy 或放宽断言。没有修改用户服务、账号、现有数据库或已发布包。

### 验证结果与边界

相同受控 fixture 下，仅加入准入后的原 40 项 core 全部通过，128.17 秒；旧失败/新通过成立。新增 failed_metadata_write_does_not_block_another_clone，以真实 SQLite trigger 拒绝单条写入后，另一 clone 的批量导入必须在十秒内完成，并验证拒绝行未写入、接受行内容正确。最终本机正常 core 41 项、严格 core Clippy、格式及 diff 检查通过。可复用 fixture、完整工作区与最终原生结果见 PR #30 的检查；验证只使用临时 SQLite，没有真实 OneDrive 端到端验收，也不证明不同实例/不同进程的永久持锁或所有 SQLite Busy 均已消失。

保留原八 writer 并发测试及 worker/扩展码诊断、错误后放行回归、Linux 慢共享 sync fixture；Windows CI 额外执行三轮 32 线程 core 套件。后续 Busy 应据阶段、扩展码及耗时区分同实例排队、外部写者和存储故障，不以重跑成功代替机制验证。

```text

```

## TD-20261006-02：dev WebDAV 适配器首轮端到端读写失败

- 日期：2026-10-06
- 状态：已验证（Linux 临时目录）；后续独立机制见 TD-20261006-03。
- 影响版本与环境：`dev` 分支新增 `twodrive-dev 0.1.0` 实验；未影响稳定程序。
- 关联历史故障：无相同实现；[provider 边界记录](refactor-2026-09-16.md) 涉及共享接口，失败在新增适配器。

### 症状与影响

首轮 PUT 返回 HTTP 500，上传上限较小时单资源 PROPFIND 返回 HTTP 502，4 项读写测试失败。已确认 PUT 错误可发生在原子替换之后；原有数据均为临时测试文件。

### 触发条件与复现

初始 8 项集成测试：4 通过、4 失败。普通、Unicode、流式 PUT 和真实本机 QUIC 转发均失败；设置 64 字节上传上限后，174 字节 PROPFIND XML 也被拒绝。

### 根因与证据

- cap-std 的 Linux 目录能力可能使用 O_PATH。复制能力句柄后直接 fsync 返回 EBADF（脱敏诊断为 errno 9），此时文件已同步、已 rename；HTTP 500 并不说明写入未发生。
- 把上传上限应用到全部方法的请求 body，误拒绝 PROPFIND XML；该错误被 DAV 库转为 HTTP 502。
- 本轮源码检查另发现普通文件检查原位于 open 之后，根目录中的 FIFO 可阻塞读取。直接命名管道回归覆盖该路径，增加 open 前类型检查及 Unix O_NONBLOCK，之后再检查句柄类型，防止本机替换竞态使网络读取阻塞。

### 解决办法与恢复操作

以目录能力重新打开可读父目录句柄并同步，保持访问范围约束；文件体上限只用于 PUT，XML 采用独立 64 KiB 上限。Content-Length 和实际流长度超限返回 413，中断/超限写入删除临时文件，保留原内容；命名管道与设备不作为普通文件打开。未操作真实账户、用户目录、系统服务或安装包。

### 验证结果与边界

- 修正前 PUT/小上限元数据测试失败（500/502），修正后通过。`interrupted_and_oversized_put_preserve_original_content` 核对原内容与临时文件清理；元数据读取不受 64 字节上传上限影响。
- `capability_scope_rejects_symlink_escapes_and_special_files` 覆盖外部目录/文件软链接、设备软链接、命名管道、`..` 和保留临时文件名。临时移除普通文件检查和非阻塞打开后，旧机制的单项回归在编译完成并进入测试后超过 12 秒，被隔离测试超时终止（退出 124）；恢复保护后该项通过。
- 权限、过期/单次/并发邀请、真实 QUIC 未授权拒绝和现有连接撤销测试通过。验证为临时磁盘与本机设备，未覆盖所有文件系统的断电恢复、磁盘故障或 Windows ACL 部署。

### 防复发措施与后续

保留文件提交后响应、上传错误不破坏原内容、独立 XML 限制与 capability 范围回归；无法声称所有 500/502 错误永久消失。其他新机制和完整测试范围见 TD-20261006-03。

## TD-20260916-01：C 编译产物在挂载中无法执行

- 日期：2026-09-16
- 状态：已验证本地权限机制修复（真实 FUSE 挂载 + MockBackend）；未验证真实 OneDrive 端到端。
- 影响版本与环境：修复前源码 `2f2607a`（基于 v0.2.9-1）；用户运行版本及具体产物未核实。修复版本 0.2.10-1。
- 关联历史故障：[早期可靠性修复](reliability-fix-2026-07-24.md)，其 setattr 兼容处理仅确认请求，没有保存 POSIX mode。本次补齐该处理遗漏的本地权限功能；与 TD-20260915-01 的本地创建记录丢失机制不同。

### 症状与影响

用户报告在 TwoDrive 创建 .c 文件后，编译结果无法执行。隔离复现中编译成功，但运行报 Permission denied；chmod 调用成功却不改变可见权限。

### 触发条件与复现

在隔离 MockBackend FUSE 挂载中创建 `hello.c`，内容为 `int main(void) { return 0; }`，执行 `cc hello.c -o hello`，再执行产物并尝试 `chmod 755 hello`。修复前产物及 chmod 后权限均为 0644，执行报 errno 13。将同一源文件编译输出到本地普通目录后可运行。

### 根因与证据

修复前 `crates/twodrive-fs/src/lib.rs` 的 `attr_for_record` 把普通文件权限固定为 0644；`create` 忽略 mode/umask；`setattr` 忽略 mode。因此无法保留编译器或 chmod 设置的执行位。初次使用现有 debug 二进制复现（其构建提交未核实）后，又将新增编译/挂载回归测试放到未修改的源码上重新构建：测试稳定失败，实际权限为 `0o100644`。修复后同一编译执行流程通过。本机原挂载选项未见 noexec。

### 解决办法与恢复操作

- 为 SQLite files 增加可空的 local_mode 字段，按稳定本地身份保存普通 rwx 位。迁移可重复执行；旧条目及新导入的云端条目仍默认文件 0644、目录 0755。
- 创建文件和目录时，把 `mode & !umask & 0777` 与本地创建记录一起持久化；chmod 更新数据库及 inode 视图，不产生内容上传任务。启用 FUSE default_permissions，让内核检查本地权限。
- 上传确认、单条/批量云端更新、释放缓存及重命名保留本地权限；原子替换使用来源文件权限，不能错误继承目标文件权限。重挂载从数据库恢复。
- 已有编译产物升级并重挂载后可用 `chmod +x 文件名` 恢复执行，也可重新编译。权限只保存在本机，不作为云端元数据同步。

本地恢复操作：仅创建并卸载隔离测试挂载；未安装到用户运行目录、重启用户服务或修改用户的云端文件。deb 更新需另行安装并重挂载后生效。

## TD-20260916-02：relay-lab 原型的云端信任与控制重放边界不足

- 日期：2026-09-16
- 状态：已验证新 peer 的本地及原生 CI 安全机制；真实 OneDrive 端到端未验证。
- 影响版本与环境：用户提供的独立 twodrive-relay-lab 0.1.0 原型；不据此认定稳定 TwoDrive 存在相同攻击面。
- 关联历史故障：无；与 FUSE 权限和本地创建记录故障无关。

### 症状与影响

原型把同一 OneDrive 中自签名 manifest 列表作为 trusted_senders；可写云端的主体能添加自有密钥，再发送可被接受的加密消息。加密不等于验证物理设备归属。原型没有设备控制握手与会话重放状态，不能直接当作控制协议使用。

### 触发条件与复现

审计 identity.rs 的 manifest 自签名验证、graph.rs::list_manifests 和 crypto.rs::verify_payload 调用链，确认信任列表完全来源于云端。新协议用未知自签名设备、重复信封、过期信封、错误会话/目标作为合成回归输入。旧原型复制到隔离临时目录后，新增两项安全要求测试；均可重复失败（云端注入身份被接收、同一信封两次解密均被接收）。原始工作区原型未修改，也未在真实云端进行攻击测试。

### 根因与证据

云端发现与本地授权未区分；消息签名未覆盖目标、信封 ID 和有效期等外层路由字段。详细分析见 [peer audit](peer-implementation.md)。Windows 兼容性检查还发现已有 core credential 和 provider upload persistence 导入 Unix 专用 API，原样依赖无法编译 Windows peer；这属于此前 Linux-only 代码的移植边界。

### 解决办法与恢复操作

复用 provider/OAuth，不导入原型的重复认证实现。新协议增加本地指纹信任、完整上下文签名、随机会话、挑战握手、重放窗和输入上限。Windows 使用 DPAPI，Unix 保持 token 格式兼容并原子写入。更新发布密钥独立于设备身份和云端。

本地恢复操作：无。仅在独立 worktree 和测试临时目录构建运行，未操作稳定服务和已有用户数据。

### 验证结果与边界

初轮 peer 7 项、core 31 项 Linux 测试通过，包括未知设备拒绝、双向握手与 ping/pong、重放/过期/会话拒绝，以及正常更新、错误签名、损坏文件、健康检查失败回退。最终 110 项默认 Rust 测试、19 项 Python 测试、6 项实际隔离 FUSE 测试、独立 daemon smoke 通过。Windows 原生 CI 的 68 项默认测试及额外原生更新进程测试通过。测试为模拟，非真实 OneDrive 端到端。已在原型副本运行 audited_cloud_manifest_is_not_local_authorization 和 audited_control_replay_must_be_rejected，两项均因预期的安全边界缺失而失败；新 peer 的对应未知身份和重放拒绝测试通过。两套实现协议不同，这不是将同一测试直接移植到旧生产版本。

### 防复发措施与后续

协议层测试固定 cloud discovery != local trust；后续传输仅提供不可信字节。保持独立发布根、反回滚检查和不覆盖当前 exe 的更新事务。更多故障及最终验证将在交付前补记。

## TD-20260915-01：新建目录中解压文件报 I/O 错误

- 日期：2026-09-15
- 状态：已验证本次故障机制修复；真实 OneDrive 完整上传、下载比对尚未执行。
- 影响版本与环境：修复前源码包含于 0.2.8；故障发生在 Linux/Nautilus + TwoDrive FUSE 挂载。本机旧程序早于本次发布，具体包版本未核实；不据此断言最早受影响版本。
- 关联历史故障：[父目录移动与子项同步顺序](folder-move-sync-2026-09-11.md)。关联在于保护待处理目录的逻辑；没有证据证明此前所有 I/O 错误都是本次根因。

### 症状与影响

向 OneDrive 挂载中新建的目录解压 ZIP，创建 `__MACOSX/._…` 文件时出现输入/输出错误。守护进程记录：`twodrive create upload error: created upload record disappeared`。

失败会中断解压并留下部分结果。普通文件也受影响，`._` 文件名只是本次最先暴露问题的位置。原 ZIP 的 48 个条目通过 CRC 检查；未发现原压缩包损坏的证据。

### 触发条件与复现

1. 在本地建立目录，使其云端创建操作仍处于待处理状态。
2. 在其中建立嵌套目录并创建文件，例如解压 ZIP。
3. 在父目录同步完成前执行本地文件创建。

隔离测试中保留父目录待处理状态，可稳定触发旧代码错误。待移动父目录使用同一过滤机制；新增解压测试直接覆盖的是待创建目录。

### 根因与证据

`TwoDriveFs::create_upload` 将本地新建文件交给 `Database::upsert_metadata`，随后再分别登记缓存和 Writing 状态。

`upsert_metadata` 用于云端元数据导入。为防止过时云端数据破坏尚未完成的本地目录操作，它会跳过待创建或待移动目录下的条目。此次本地写入也被跳过，函数却正常返回；后续查询找不到记录，最终向 FUSE 返回 EIO。

将新增回归测试放回旧 `create_upload`，稳定得到与生产日志完全相同的错误。修复后同一测试通过。原来的分步写入还暴露了中间状态；本次一起消除了这个窗口，但没有把它当成已证实的另一条生产故障原因。

### 解决办法与恢复操作

新增 `Database::create_local_file`：通过单条 SQLite INSERT 同时登记本地身份、路径、缓存路径、访问时间和 Writing 状态。本地创建不再经过云端导入过滤；唯一约束防止覆盖同名记录。

保留云端旧元数据过滤和父目录操作完成前暂停上传的规则。新建内容由写入句柄持有缓存锁，后续按原有恢复流程上传。

本地恢复：备份数据库和旧程序后更新用户目录下的 CLI、daemon，并重启服务；挂载恢复，真实 OneDrive 元数据同步成功。没有自动合并或删除历史部分解压结果和无关云端冲突。

### 验证结果与边界

- 87 项默认 Rust 测试、19 项 Nautilus 测试通过；格式检查及 Clippy（警告视为错误）通过。
- 5 项通常忽略的实际 FUSE 挂载测试全部显式执行并通过，包含待处理目录中的 ZIP 解压。
- 普通文件和 AppleDouble 文件在父目录待处理时保留正确字节，父目录恢复后向模拟云端正确上传；过时元数据未替换本地记录。
- 验证了待删除路径重用及同名创建冲突时保护现有记录。
- 安装包内容和构建输入一致，GitHub 安装包摘要与本地 SHA-256 一致。
- **验证边界**：挂载测试的云端为 MockBackend。真实 OneDrive 只验证了元数据同步与原 ZIP 读取校验，未完成原 ZIP 的“解压 → 上传 → 重新下载逐文件比对”。不能据此保证任何来源的 I/O 错误都不会再发生。

### 防复发措施与后续

已提交的回归测试：
