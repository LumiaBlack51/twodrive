# Responsibility-based refactor, 2026-09-16

This branch preserves the 0.2.10 behavior and storage formats. It adds no provider,
relay, NAT or Windows peer functionality. Base: `95c0f3f`. It is intentionally not
merged into main. Package revision: **0.2.10-2**; Rust/CLI version remains 0.2.10.

## Ownership and boundaries

- **Core**: `domain.rs` holds metadata, local state and pending-work values;
  `paths.rs` and `time.rs` hold shared primitives. `config/` retains TOML defaults
  and `credentials.rs` retains the compatible token-file format and permissions.
  `database/` separates schema/migrations, metadata import and acknowledgement,
  local mutations and durable work, cache transitions, pin inheritance and queries.
  SQL, transactions, migration ordering and local/cloud identity semantics remain
  unchanged. Private connection and row decoding helpers stay inside persistence.
- **Backend**: `storage.rs` owns `CloudBackend` and `DeltaResult`; `mock.rs` is
  independent of the Graph transport. `onedrive/` owns Graph mapping, URL encoding,
  HTTP retry, OAuth/PKCE, token refresh and resumable upload sessions. Root exports
  remain compatible. The filesystem asks the backend to classify version conflicts;
  the default preserves historical error-text behavior for existing implementors.
  Future providers can override this classification without teaching FUSE HTTP.
- **Filesystem**: metadata reconciliation, recovery, hydration/pinning, conflict
  preservation, activity output, upload scheduling, per-item locks, read workers,
  inode views and cache I/O have separate modules. `filesystem/` owns live handles,
  local read/write/mutation operations and the FUSE adapter. `mount.rs` is the
  composition point for mock/OneDrive creation and the recovery thread lifecycle.
- **Daemon**: main only starts the selected service. `known_folders/` separates
  watcher events/debounce, local traversal, upload execution, persisted snapshots
  and activity presentation. Upload-only and no-delete semantics are unchanged.
- **CLI**: main dispatches commands; arguments, operations and desktop/status
  presentation have separate modules. Python desktop integration is unchanged.

The library roots contain 9/23/23 lines (backend/core/fs), and the executable
entry points 49/24 (CLI/daemon) at extraction. Responsibilities, not these counts,
determine the module boundaries. Internal implementation types are not newly
exported as root APIs.

## Compatibility seams and remaining debt

The `[graph]` TOML schema/defaults and `Config::validate_graph_login` live in
`core/config/onedrive.rs` as a compatibility schema, avoiding a core/backend
cycle. Graph network/authentication implementation is entirely in the provider.
`Database::delta_link` retains the existing `onedrive_delta_link` database key;
`DeltaResult::delta_link` is an opaque provider cursor. Renaming these persisted
fields or adding multi-account/provider configuration is intentionally deferred.
Version conditions (`etag`, `if_match`) remain opaque strings. The old trait
fallbacks (including ignoring conditional upload arguments) are preserved, not
silently strengthened during a refactor. A future provider needs explicit
capability/conditional-write contracts and its own integration tests.

`TwoDriveFs` still coordinates multiple state machines, while database mutations
and FUSE dispatch remain the largest production modules. Further redesign would
require behavioral work, beyond moving ownership boundaries. Filesystem and
known-folder activity files still use different schemas/locking and are not
merged merely because both emit JSON. Existing public compatibility/recovery
methods and test-only upload helpers remain available.

## Safe cleanup

Removed the duplicate filesystem `current_unix_i64` implementation; activity
reporting and tests now use the byte-for-byte equivalent core `now_unix` helper.
Removed imports made unnecessary by module ownership and replaced provider
internal wildcard imports with explicit dependencies. Reviewed all direct Cargo
dependencies against usage: **none were established to be unused**, so none were
removed. No migration, recovery path, incident logic or public compatibility API
was deleted. No lockfile dependency upgrade was introduced.

## Limits and incident policy

These are MockBackend and loopback HTTP tests, **not real OneDrive end-to-end
verification**. No new real OAuth login, cloud upload/download round trip or
interactive desktop session was tested. Unit-tested known-folder behavior does
not establish real Graph watcher end-to-end behavior. No live database, cache,
token or account file was used by the refactor tests.

This is not a new incident fix. Existing mechanisms and records in
[incidents.md](incidents.md) were preserved; no newly discovered reproducible
product defect required a new incident entry. Prior incident verification limits
still apply. The user subsequently authorized replacing/restarting the application
after validation; no computer reboot or main-branch merge is authorized.
